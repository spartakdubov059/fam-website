# Рабочая модель ИИ и команды FAM

Обновлено: 10 ноября 2026 года.

Документ разделяет реально работающие серверные ИИ-компоненты, защитные механизмы и роли команды разработки. Серверные агенты работают внутри защищённых Supabase Edge Functions; ключи OpenAI доступны только серверу.

## 1. Иерархия модерации

### Главная серверная функция — `moderate`

Она принимает текст, изображения и контекст отправки, применяет локальные проверки и направляет данные нужному OpenAI-компоненту.

1. **Локальный фильтр контактов.** До внешнего API выявляет телефоны, адреса, почту, ссылки и публичные никнеймы. Подходящие сигналы блокируются без передачи текста модели.
2. **OpenAI Moderation — `omni-moderation-latest`.** Первая классификация текста и/или изображения на потенциально вредный контент.
3. **Агент «Эксперт FAM» — GPT-5-mini.** Только контекстная перепроверка спорного текста после первого этапа. Может одобрить явно нейтральный контекст, отклонить нарушение или оставить материал на проверке.
4. **Агент-модератор идей — GPT-5-mini.** Отдельный режим для каждой новой идеи: спам, реклама, травля, оскорбления, личные негативные призывы и неоднозначные обвинения. Конструктивная критика школы разрешена.
5. **Агент фотографий — GPT-5-mini.** Проверяет фото объявлений и аватары до публикации: соответствие назначению, личные данные, QR-коды, документы, постороннюю рекламу, травлю и небезопасное содержимое. Не идентифицирует людей и не определяет личные характеристики.

Высокорисковые категории не могут быть одобрены контекстным вторым этапом. При сбое, неясном ответе или спорном результате материал не публикуется автоматически.

## 2. Агент безопасности пользователей

Отдельный модуль `user-safety-agent.ts` получает структурированные результаты модерации и собирает обезличенные сигналы из:
- личных сообщений;
- почты идей;
- объявлений;
- изображений и аватаров.

Он группирует повторные сигналы по школе и псевдонимному отпечатку пары/автора, считает количество и время эпизодов. Несколько повторов повышают уровень внимания; прямые угрозы, ненависть и некоторые особо серьёзные категории сразу дают высокий уровень.

**Что хранится:** школа, тип источника, категория, уровень, время и HMAC-SHA-256 отпечаток, вычисленный серверным секретом. Это позволяет группировать повторные сигналы, но не позволяет сопоставить их с известными ID учеников только по выгрузке базы. Тексты сообщений и прямые ID учеников в таблицу инцидентов не записываются. При ротации серверного ключа группировка старых и новых сигналов начнётся заново.

**Что не отслеживается:** клики, просмотры страниц, местоположение, история браузера и психологические характеристики. Агент не ставит диагнозов и не выносит решения о виновности.

Сводка за последние 30 дней видна уполномоченному администратору школы в профиле. В интерфейсе отображаются категории и повторяемость, а не содержимое частных переписок. Серьёзные ситуации передаются ответственному взрослому школы. Сигнал ИИ — повод проверить ситуацию, а не доказательство нарушения.

## 3. Серверные функции Supabase

| Функция | Роль |
|---|---|
| `moderate` | Оркестрация OpenAI-модерации, идей, фото и сигналов безопасности |
| `submit-content` | Проверка сессии, лимитов, отправка текста/фото и безопасное сохранение |
| `school-admin-access` | Заявки на полномочия Ученического совета и администратора |
| `council-management` | Действия Совета, администраторские операции и сводка безопасности |
| `fam-agent-worker` | Исполнение только разрешённых задач из закрытой очереди и агрегированная проверка её состояния |

Серверные функции не являются самостоятельными моделями. Они применяют проверку авторизации и секреты Supabase.

## 4. Команда разработки

Рабочие роли команды:
- **Координатор:** приоритеты, согласование и границы ролей.
- **Разработчик:** код сайта, Edge Functions и миграции.
- **Общий тестировщик:** пользовательские сценарии и регрессии.
- **Аналитик:** внешние исследования и сравнение решений.
- **Агент-модератор:** качество правил и разбор ошибок классификации.
- **Агент-безопасник:** RLS, роли, ключи, Storage, CORS и журналы.
- **Документатор:** README, CHANGELOG, версии и инструкции.
- **Тестировщик русского контента:** сленг, опечатки, транслит, контекст и ложные срабатывания.

Это роли процесса, а не восемь постоянно работающих независимых моделей. Реально активные серверные функции перечислены в разделе 3.

Для разработки кода подготовлен отдельный ручной workflow **FAM Codex developer** в GitHub Actions. После проверки и объединения его PR, добавления отдельного GitHub Actions secret `OPENAI_API_KEY` и настройки бюджета владелец сможет вручную передать ему задачу. Codex работает в отдельной копии репозитория, не получает GitHub-права на запись, не может менять базу и не публикует сайт. После независимой проверки он может подготовить только черновой Pull Request. Публикация остаётся отдельным решением владельца. До выполнения этих условий Codex-разработчик не считается активированным.

## 5. Границы безопасности

- Не анализировать клики или поведение вне материалов, которые отправляют на FAM.
- Не хранить тексты частных сообщений в журнале безопасности.
- Не показывать школьному Совету частные переписки или данные, которые ему не нужны.
- Не делать выводов о личности, возрасте, здоровье или психологическом состоянии человека по фото или тексту.
- Не применять санкции автоматически только по сигналу модели.
- Не отправлять сомнительные материалы на повторный генеративный разбор, если первичная проверка отметила высокорисковую категорию.
- Серьёзные случаи рассматривает ответственный взрослый; ИИ не заменяет школьную процедуру защиты детей.
- Все тестовые примеры должны быть вымышленными.

## 6. Ежедневная аналитическая команда

Ежедневно в 06:00 UTC для каждой школы формируется отдельная сводка. В неё попадают только агрегированные числа: активные и новые объявления, обезличенные сигналы безопасности, обращения на рассмотрение и идеи, ожидающие Совет.

На этих числах работают четыре бесплатных аналитических правила:
- `fam_safety_analyst` — предлагает проверить непроверенные сигналы безопасности; не определяет виновность и не назначает санкции.
- `fam_council_analyst` — напоминает Совету о новых идеях учеников.
- `fam_operations_analyst` — напоминает администратору о нерассмотренных обращениях.
- `fam_growth_analyst` — замечает пустую доску и предлагает проверить её наполнение и удобство.

Предложения создаются не чаще одного раза на правило в день для каждой школы, чтобы повторный запуск расписания не создавал дубли. Доступ к просмотру и решению имеет только администратор соответствующей школы. Одобрение/отклонение сохраняется в журнале; это не запускает изменения кода, не удаляет аккаунты и не вводит ограничения.

**Ограничение по стоимости:** эти четыре ежедневных аналитических правила работают в PostgreSQL без дополнительных обращений к платной языковой модели. Они не являются четырьмя отдельными генеративными ИИ-моделями. Генеративный ИИ-аналитик оставлен выключенным, пока не согласован отдельный бюджет API.

## 7. Границы доступа к сводкам

- У каждой школы своя строка отчёта и свой список предложений.
- Отчёты содержат счётчики и категории, а не тексты сообщений, прямые ID участников, телефоны, адреса или адреса электронной почты.
- Внутренние таблицы и RPC недоступны `anon` и `authenticated`; чтение/решение проходит через проверяющую роль серверную функцию.
- Сигнал безопасности — повод для человеческой проверки, а не доказательство нарушения. Серьёзные случаи передаются ответственному взрослому.

## 8. Фоновый исполнитель и облачная разработка

**fam-agent-worker** — активная Supabase Edge Function. Это детерминированный исполнитель заранее разрешённых заданий, а не генеративная модель и не программа на пользовательском компьютере. Он работает в Supabase независимо от состояния ноутбука.

Worker вызывается через активный pg_cron job каждые 5 минут. Вызов использует отдельный секрет `fam_agent_worker_token` из Supabase Vault и заголовок `x-fam-agent-token`. Проверка токена находится внутри самой Edge Function; `verify_jwt=false` не означает отсутствие защиты.

Текущий allowlist содержит ровно четыре типа задач, все с `approval_required=false` и только для чтения агрегированных технических показателей:
- `quality / queue_health_check` — число ожидающих, захваченных и выполняющихся заданий, ошибки и просроченные аренды;
- `orchestrator / daily_report_digest` — сводные рабочие счётчики FAM;
- `technical / system_health_check` — наличие служебных расширений, расписаний, права RPC и агрегаты очереди;
- `technical / site_error_digest` — агрегированные фиксированные коды клиентских ошибок и разделы сайта.

Неизвестный тип задачи блокируется. Worker не читает частные сообщения, текст объявлений, содержимое payload задач или персональные данные; он не меняет исходный код, не выполняет миграции и не принимает решения по пользователям.

Расписание вспомогательных проверок:
- опрос Worker — каждые 5 минут;
- формирование школьных ежедневных отчётов — 06:30 MSK;
- техническая проверка системы — 06:40 MSK;
- ежедневная сводка координатора — 07:00 MSK;
- аудит агрегированных ошибок сайта — ежечасно.

Отдельная ChatGPT-автоматизация формирует единый подробный отчёт для владельца. Она не является постоянным процессом и запускается по дневному расписанию.

**ИИ-разработка исходного кода — отдельный контур.** Для неё подготовлен проект workflow на базе официального OpenAI Codex Action. Он запускается вручную владельцем после включения workflow и настройки отдельного API secret и бюджета. Codex редактирует только разрешённые файлы сайта/документации/тестов в изолированной копии. Независимый job выполняет проверки без API-ключа; третий job может создать черновой PR. Автоматического merge, production deploy, изменений Supabase или действий с аккаунтами нет. Этот контур не считается активным до настройки ключа, ручного запуска и успешной проверки всей цепочки.
