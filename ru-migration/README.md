## Восстановление незавершённого удаления аккаунта (18 ноября 2026)

Начало удаления атомарно деактивирует профиль и создаёт durable-задание в `fam_account_deletion_jobs` с пятиминутной lease. После сбоя до первой попытки удаления файла профиль и заявка возвращаются в исходное состояние. После начала удаления файлы никогда не возвращают профиль в активное состояние: задание сохраняется, а отдельный ручной запуск после истечения lease повторно перечисляет только ключи владельца, удаляет их и завершает YDB-очистку в одной транзакции.

Операторская команда для изолированной конфигурации: `node ru-migration/app/backend/recover-incomplete-account-deletions.mjs`. Команда обрабатывает максимум 10 заданий за запуск; автоматический таймер и новые облачные ресурсы не включаются. Схема `30_account_deletion_jobs.yql` должна быть применена до использования этой версии backend. Локально прошли `295/295` backend-тестов и `ru-migration/compat/verify.mjs`; [одноразовая YDB CI-интеграция](https://github.com/spartakdubov059/fam-website/actions/runs/44211677033) успешно применила схемы 01–30 и проверила ручное возобновление на синтетической записи, а [SDK/Sharp CI](https://github.com/spartakdubov059/fam-website/actions/runs/44211676979) прошёл. ## Что уже реализовано в изолированном коде

- Отдельная копия статического интерфейса в `app/web`.
- Fail-closed HTTP backend с API подачи объявления и школьной идеи; для идей без внешней модели применяется бесплатный локальный fallback исходного FAM: неотмеченные идеи проходят локальный этап и направляются в школьную очередь, серьёзные маркеры угроз/ненависти остаются `pending`, а другие локально запрещённые темы отклоняются.
- Избранное подключено к публичной доске: вошедшие пользователи добавляют и удаляют активные объявления; гости переходят на Яндекс ID, а записи выполняются только от подтверждённого профиля.
- API и UI личных сообщений: с карточки можно обратиться к автору активного объявления; сервер сам определяет получателя и ограничивает его той же школой. Диалоги доступны только участнику. Пока классификатор не подключён, сообщение записывается в закрытую очередь `pending` и не показывается получателю до одобрения активным администратором той же школы; лимит — 5 ожидающих сообщений от отправителя за 24 часа.
- Российский экран без Supabase открывает inbox из доступной кнопки: пользователь видит только собственные диалоги, может читать историю и отправлять текст в ручную проверку. UI-тесты прошли на Node 22 в commit `28df4c2a20e060f570a2200a86c90685b45ff098`; решение принимает школьный администратор, автоматический классификатор не настроен.
- OIDC bearer verification и разрешение ролей через профиль в YDB. Дополнительно реализован серверный OAuth Яндекс ID с PKCE S256, одноразовой state-cookie, проверкой `client_id` профиля, часовым HttpOnly/SameSite cookie и logout. Для unsafe-запросов по cookie и logout требуется точное совпадение `Origin` с origin зарегистрированного callback.
- Маршрут школьной модерации объявления: права берутся из профиля YDB, решение ограничено школой объявления и переходом только из `pending`; используется транзакция YDB.
- Добавлен backend-модуль записи на мероприятия: открытые и ограниченные события, одно место на пользователя, транзакционная проверка вместимости, отмена своей записи, публичный счётчик без данных участников и решение владельца мероприятия с ролью школьного администратора/совета.
- Гостевая доска показывает дату и время мероприятия; пользователь может войти через Яндекс ID, записаться или отменить свою запись. Кнопки используют только same-origin запросы; HTML пользовательских полей не вставляется в DOM.
- YDB схема профилей и объявлений, параметризованный repository; добавлено публичное чтение только активных объявлений с ограниченным набором полей; `/api/v1/me` возвращает профиль из YDB только после проверки OIDC-токена.
- Локальные privacy/moderation gates; новые записи остаются `pending`, если проверка недоступна.
- Временные ограничения аккаунтов: отдельная таблица сохраняет события ограничения, а общий серверный барьер блокирует авторизованные записи в API объявлений и медиа при активном ограничении; при невозможности проверить статус запись отклоняется с 503. Чтение остаётся доступным. Схема и синтетический путь прошли одноразовую YDB интеграцию. Административная выдача/снятие ограничений, свежая аутентификация, аудит и UI перенесены в изолированную ветку.
- При повторном входе незарегистрированный пользователь получает только собственный статус школьной заявки; endpoint не возвращает имя, класс или subject. Интерфейс не предлагает дублировать активную заявку и позволяет повторно проверить статус; после одобрения предлагает обновить сессию/страницу, а отклонённую заявку можно отправить заново. Полный цикл проверен синтетически.
- Ученик с одобренным школьным профилем может запросить одну из двух фиксированных ролей. Решение принимает администратор той же школы, который ранее закрепил заявку за собой; изменение профиля и три перехода заявки записываются в аудите без PII. Yandex ID не предоставляет проверенный эквивалент `email_confirmed_at`; поэтому текущий допуск основывается на уже одобренном школой профиле и решении администратора. Это отличие от исходной проверки email должно пройти отдельную оценку перед реальными пользователями.
- API приватной загрузки изображений: только активный профиль, JPEG/PNG/WebP до 5 МБ, проверка формата и преобразование Sharp в WebP, серверный случайный ключ с префиксом пользователя и приватный S3-совместимый объект с шифрованием на стороне хранилища. Без S3-конфигурации маршрут возвращает 503.
- Добавлены реестр загрузок `fam_pending_media` …222 tokens truncated…т роль и владельца, удаляет избранное и зависимые регистрации/счётчик события в транзакции. Медиа удаляется сервером по временной аренде; сбой хранилища оставляет ограниченную возможность повтора. API, интерфейс и YDB путь прошли CI на синтетических данных.- Форма российской копии загружает фото через тот же backend, привязывает приватный ключ к новому объявлению и отправляет объявление на проверку. Если запись объявления не удалась, браузер запрашивает удаление ещё не связанного файла; backend проверяет владельца и отсутствие ссылки из объявления. Отдельная очередь модерации показывает pending-объявления только школьному администратору/совету школы из его профиля; фото можно проверить и принять до публикации объявления. Публичная доска показывает только одобренное фото активного объявления через same-origin маршрут с `image/webp`, `nosniff` и `private, no-store`. Межшкольный доступ проверяется тестами. Для файлов, оставшихся после закрытия вкладки или потери сети, подготовлены безопасная очистка по lease в YDB и выключенный systemd timer; запуск зависит от настроенной российской среды.
- Российская форма позволяет отправить школьную идею через защищённый API; при отсутствии внешней модели она использует источник-совместимый локальный fallback, а школьное решение остаётся отдельным этапом. В карточке объявления можно написать его автору; получатель определяется сервером по активному объявлению и разрешён только в той же школе. Вкладка сообщений загружает только собственные диалоги и позволяет отвечать. Маршруты защищены тестами, межшкольный запрет сообщений проверен на одноразовой YDB. Провайдер модерации сообщений не настроен: сообщения fail closed и не сохраняются до внешнего решения `ok`.

### Подключение Яндекс ID (пока не настроено)

Для отдельного тестового домена нужно зарегистрировать приложение Яндекс OAuth типа «Для авторизации пользователей», добавить HTTPS Redirect URI `https://<тестовый-домен>/auth/yandex/callback` и минимальное право `login:info`. В переменные окружения backend передаются `FAM_RU_YANDEX_CLIENT_ID`, `FAM_RU_YANDEX_REDIRECT_URI` и случайный `FAM_RU_SESSION_SECRET` длиной не менее 32 байт. При OIDC-входе также требуется отдельный `FAM_RU_SAFETY_HMAC_KEY` длиной не менее 32 байт; при входе через Яндекс ID он может быть явно задан или использовать секрет сессии. Ключ нужен для школьного HMAC-отпечатка и не сохраняется в базе; без него сигнал угрозы/дискриминации не пройдёт дальше проверки. Секреты не записывать в репозиторий или frontend. Для разработки допустим только `localhost` без HTTPS; удалённый адрес без HTTPS отклоняется.

Обмен кода и запрос профиля выполняются сервером. OAuth-токен не сохраняется и не передаётся в URL; браузеру выдаётся только подписанная краткоживущая HttpOnly cookie. Роли выдаются исключительно из `fam_user_profiles`; сам вход не создаёт профиль и не назначает роль. Для неизвестной личности доступна заявка на школьный профиль: каталог школ задан на сервере, пользователь не выбирает роль, новый профиль появляется только после решения администратора той же школы, и всегда получает роль `student`. Решение и приватные интеграционные сценарии проверены на синтетических данных в CI. Реальная регистрация OAuth-приложения и внешний вход не проверялись. Заявки на профиль настроены на YDB TTL `P30D` по `created_at`; истёкшие записи YDB удаляет в фоне, точный момент очистки не гарантируется. Резервные копии облачной базы не настроены и их удержание не проверено.

Эти части ещё не образуют полный перенос FAM. Требуются перенос и аудит всех исходных функций, SQL/RLS, ролей и фоновых задач, а также проверка всей пользовательской навигации и сценариев.
