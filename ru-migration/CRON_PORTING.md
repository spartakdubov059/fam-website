## Ручная сводка по RU очередям отчётов

Оператор может выполнить `node ru-migration/app/backend/check-background-queues.mjs` в уже настроенной конфигурации RU backend. Команда читает агрегированные статусы из очередей отчётов и allowlisted `fam_agent_tasks`: ожидание, захват, завершение, блокировки/ошибки за 24 часа, просроченные lease и возраст самой старой записи. Она не читает payload, сводки, текст, идентификаторы пользователей или сообщения; таймер не создаётся. Общая очередь ограничена четырьмя служебными типами и не эквивалентна произвольным задачам исходной `fam_agent_tasks` или пользовательским очередям модерации.

## Безопасная очистка загрузок

Российский backend содержит реестр `fam_pending_media` и CLI `ru-migration/app/backend/cleanup-pending-media.mjs`: он удаляет только неподвязанные загрузки старше семи дней, предварительно получив для каждой lease в YDB. Школьный отчёт запускается в 03:30 UTC (06:30 MSK), digest оркестратора — в 04:00 UTC (07:00 MSK), readiness — в 03:40 UTC (06:40 MSK), site-error digest — ежечасно на минуте 30 UTC; cleanup запускается раз в 6 часов. Новый безопасный worker подготовлен каждые пять минут без catch-up после простоя. Все timers не установлены и не включены: бесплатная среда не настроена. RU coder producer перенесён только как безопасная постановка агрегированной ручной проверки; bridge не запускает Qwen/модель/инструменты. Image worker заменён ручной проверкой; RU system health проверяет YDB, очереди и локальные timers, но пока не повторяет полный исходный аудит PostgreSQL прав/расширений.

## Условия переноса

- Реализовать каждую процедуру на российском backend и явно закрепить идемпотентность, блокировки, повторы и журналирование.
- Заменить прямой вызов Supabase Edge Function внутренним российским обработчиком после переноса и проверки очереди изображений.
- Рассчитать расписания в UTC, отдельно документировать нужное московское время.
- До полного переноса всех обработчиков оставить задания выключенными. Не добавлять облачные cron-сервисы, платные функции или тестовые вызовы исходных production URL.
- Запускать только в одноразовом окружении и на синтетических данных; провайдерские задания по отчётам и агентам могут обращаться к внешним моделям и отдельно требуют проверки отсутствия расходов.

## Read-only проверка состояния systemd (20 ноября 2026)

Команда `npm run check:timers` проверяет фиксированный список шести используемых RU timer units через `systemctl show` и `systemctl is-enabled`. Для каждого таймера она также проверяет результат последнего запуска парной службы и свежесть запуска (26 часов для суточных задач, 12 минут для worker timer раз в 5 минут, 7 часов для очистки медиа, 2 часа для ежечасной сводки). В вывод попадают только имена ожидаемых таймеров и булевы признаки; timestamps, журналы и данные пользователей не выводятся. Команда ничего не устанавливает и не включает. До установки службы ожидаемо возвращает ненулевой код; в macOS окружении разработки без systemd это также безопасный fail-closed результат. Структурную корректность unit-файлов отдельно проверяет `compat/verify-systemd-timers.mjs` и Linux CI.
