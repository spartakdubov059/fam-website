Это функциональные аналоги с отличиями, не полный перенос и не доказательство parity всех upstream функций.

Локальная tracking-ссылка `origin/main` отставала на `7fd4182`; проверка выполнена прямым fetch.
- Все 78 миграций ещё не сопоставлены построчно с YDB схемой и backend API. RLS, RPC и триггеры требуют проверки эквивалентности операций и границ доступа.
- Семь активных расписаний и отменённое старое задание описаны в [CRON_PORTING.md](CRON_PORTING.md). RU unit/timer-файлы не устанавливаются и не включаются автоматически.
- Полное соответствие upstream, аудит всех маршрутов/хранилищ и российский облачный staging не подтверждены. Нет настроенных Yandex OAuth, YDB/S3 credentials; реальные пользовательские данные не используются.
- RU-копия поддерживает школьные опросы с 2–8 ответами. В ревизии [`0d3be3a`](https://github.com/spartakdubov059/fam-website/commit/0d3be3a5a5b5ea0466340b1e794cff75babed647) добавлена YDB очередь для четырёх фиксированных агрегатных задач; она не получает содержимое произвольных задач и не вызывает внешние модели. Проверенная ревизия [`925c688`](https://github.com/spartakdubov059/fam-website/commit/925c688de663a61d20fcb240c9d712a3551698a6) прошла `343/343` backend-тестов, pinned SDK/Sharp, нативный WebP, экспорты SDK, 7 systemd-таймеров и disposable YDB integration на синтетических данных ([SDK CI](https://github.com/spartakdubov059/fam-website/actions/runs/44724184297), [YDB CI](https://github.com/spartakdubov059/fam-website/actions/runs/44724184197)). Плановая health-задача проверяет readiness, доступность 36 обязательных таблиц с `LIMIT 0`, таймеры и агрегированное состояние разрешённых очередей, завершаясь ошибкой при деградации; строки таблиц и права записи не проверяются. YDB CI проверяет claim/finish безопасной coder задачи и отклонение повтора завершения. Это не облачный staging и не доказательство полного переноса.
- Карта Edge Functions: `council-management`, `school-admin-access` и `submit-content` имеют частичные RU-эквиваленты; `fam-agent-worker` перенесён частично только для четырёх безопасных агрегатов; API-протокол `fam-agent-coder-bridge` перенесён для изолированных агрегированных задач, но локальный Qwen runner и генерация исправлений отсутствуют; `fam-listing-image-worker` заменён ручной проверкой без автоматической модельной модерации; `moderate` перенесён частично без внешнего AI. Это функциональные адаптации, не полная совместимость.
- RU coder producer создаёт не более одной задачи на слот только при пороге в allowlisted телеметрии и сохраняет четыре поля агрегата без пользовательского текста. Новый claim/finish bridge доступен только с отдельным `FAM_RU_CODER_WORKER_TOKEN` (не менее 32 байт), возвращает lease token и принимает фиксированные коды результата; браузерные `Origin` отклоняются, длина тела ограничена 2 КБ. Общий безопасный worker этот тип не исполняет, модель и инструменты не запускаются. Подключение self-hosted модели и доказательство её нулевой стоимости не выполнены; расписание не установлено/не включено.
- Добавлен TTL для `fam_agent_tasks` по nullable `finished_at` и для `fam_agent_task_events` по `created_at`: завершённые задачи и журнал автоматически очищаются через 180 дней, активные и незавершённые задачи с `finished_at = NULL` сохраняются. При повторном захвате worker сбрасывает `finished_at`, чтобы retention начинался от нового завершения.


Обследование исходников ветки `migration/yandex-cloud`, 13 ноября 2026. Это перечень компонентов для самостоятельного переноса по коду текущего FAM; архив предыдущей сборки не требуется для этого этапа.

## Объём исходного приложения

- Статический фронтенд в корневом `index.html`; сейчас он обращается к Supabase напрямую.
- 7 Edge Functions: `council-management`, `fam-agent-coder-bridge`, `fam-agent-worker`, `fam-listing-image-worker`, `moderate`, `school-admin-access`, `submit-content`.
- Текущий проверенный `main` `7fd418246653f92b53f66bc29fa224d95d04d5cf` содержит 76 SQL migration-файлов. Их нужно сопоставлять с российской схемой и API, а не переносить механически: YDB не исполняет Supabase RLS/RPC/триггеры. Полный построчный перенос и аудит пока не выполнены.
- В исходных миграциях перечислено 7 текущих активных расписаний `pg_cron` плюс отменённое старое `fam-agent-daily-report`; точные вызовы и статус переноса сверены в [CRON_PORTING.md](CRON_PORTING.md). Российские аналоги не устанавливаются автоматически.
- Зависимости, которые нельзя потерять: Auth и роли, приватные/публичные медиа, модерация, очереди, учёт событий, удаление аккаунта, школьные ограничения доступа и фоновые отчёты.

## Повторная проверка бесплатного российского хостинга (17 ноября 2026)

- В Yandex Cloud free tier покрывает только квоты; превышение тарифицируется. Бюджет в Billing присылает уведомления и сам по себе не прекращает потребление. Источники: [free tier](https://yandex.cloud/ru/docs/billing/concepts/serverless-free-tier) и [бюджет](https://yandex.cloud/ru/docs/billing/concepts/budget), документация обновлена в ноябре и июне 2026 соответственно.
- В Cloud.ru бессрочная бесплатная виртуальная машина доступна только аккаунтам, зарегистрированным не позднее 30 июня 2026 года. Ей нужен публичный IP или SNAT для интернет-доступа, а эти услуги оплачиваются отдельно; также документация требует положительный баланс. Поэтому такую ВМ нельзя считать гарантированно публичным хостингом за 0 ₽. Источник: [официальные условия Free Tier VM Cloud.ru](https://cloud.ru/docs/virtual-machines/ug/topics/overview__free-tier).
- Cloud.ru Container Apps даёт ежемесячную общую квоту 25 vCPU×часов и 50 GB×часов RAM для сервисов; превышение бесплатного объёма тарифицируется. Квота общая для организации, не на отдельное приложение. Источники: [Free Tier Container Apps](https://cloud.ru/docs/container-apps-evolution/ug/topics/overview__free-tier) и [активное предложение](https://cloud.ru/offers/free-tier).
- На текущих подтверждённых условиях ни один вариант не доказывает непрерывную публичную работу RU-копии с жёстким верхним пределом расходов 0 ₽. Это оставляет облачный staging без безопасного подтверждённого способа; ресурсы не создавались. Повторить эту проверку нужно до выбора хостинга, потому что правила и eligibility меняются.

## Перенесено в изолированный backend

- Частичные пользовательские сценарии: публичная доска объявлений с избранным и событиями, подача объявления с состоянием `pending` и фото, отправка школьских идей, школьная модерация текста/фото/заявок на события. API, UI личных сообщений и обращение автору активного объявления подключены; получатель берётся сервером из объявления, сообщения ограничены школой. Без внешнего классификатора текст записывается только в закрытую очередь `pending` и не доставляется собеседнику до решения модератора той же школы; ручная очередь и approve/reject подключены. Личный кабинет и часть школьской навигации перенесены, но полное сопоставление исходной навигации и пользовательских сценариев не завершено.
- В сценарии без Supabase входящая переписка доступна из основной RU-оболочки; отправка сообщения с объявления появляется в том же inbox. UI-тест включён в успешный Node 22 прогон (`144/144`) commit `28df4c2a20e060f570a2200a86c90685b45ff098`.
- Добавлен модуль API записи на мероприятия: уникальная запись пользователя, транзакционная проверка ограниченной вместимости, отмена участником, счётчик мест без раскрытия записавшихся и решение по заявке владельцем мероприятия с проверкой роли и школы.
- Форма школьного Совета и администратора создаёт мероприятие с датой, временем, открытой записью, заявкой или лимитом до 500 мест; роль ученика не получает категорию «Мероприятия». Payload формы проверен синтетическим UI-тестом в Node 22 CI и локальном прогоне `145/145` на commit `893a318e599f98ea79159535c712dc93763ddb11`.
- Гостевая доска показывает детали мероприятия и поддерживает вход, запись, отмену своей записи. Backend позволяет школьным администраторам и совету просматривать минимальные данные заявок только по своей школе; экран школьной модерации подключён: сотрудники школы видят очередь ожидающих заявок и могут подтвердить или отклонить их; список ограничен школой и содержит только имя и класс заявителя. Схема проверена на одноразовой YDB в CI, но остаётся тестовой: перед облачным запуском нужны отдельная миграция базы и бесплатное окружение с контролем расходов.
- Приватный API загрузки фотографий подключён к форме российского UI: принимает ограниченные типы и размер, нормализует файл в WebP и сохраняет его по серверному ключу в приватном S3-совместимом бакете. Ключ связывается с pending-объявлением; при ошибке отправки UI просит сервер удалить ещё не привязанный объект, а backend отказывает в удалении объекта, уже используемого объявлением. Школьный модератор видит в same-origin очереди только pending-объявления своей школы и может одобрить фото перед публикацией объявления. Публичный UI отображает только одобренное фото активного объявления через серверный маршрут. Проверены межшкольные запреты, передача бинарных данных, UI очереди и удаление незакреплённого объекта. Очистка реализована CLI, DB lease и выключенным по умолчанию systemd timer: удаляются только принадлежащие backend записи pending media старше 7 дней или просроченные lease; произвольные ключи бакета не сканируются. Синтетические сценарии есть в backend и disposable YDB CI. Timer не установлен и не включён, пока нет безопасного staging и лимитов хранения.
- Для брошенных загрузок добавлен реестр `fam_pending_media`, атомарная привязка к объявлению и CLI-сборщик. До удаления YDB выдаёт lease для неподвязанных файлов старше 7 дней; привязанные файлы исключаются, неудачные удаления могут повторяться после lease. Жизненный цикл проверен на одноразовой YDB в CI; автоматический запуск/cron не включён.
- Автоматическая очередь модерации изображений и исходная Edge Function `fam-listing-image-worker` не перенесены. Российский API хранит фото приватно и даёт доступ к очереди только школьным модераторам той же школы; публикация с фото невозможна до явного одобрения. Проверенного бесплатного российского сервиса автоматической проверки нет, поэтому внешний классификатор не подключён, а оригинальный Supabase URL не вызывается.
- Добавлено удаление собственного активного объявления для роли `student`: закрытый endpoint выдаёт пользователю только его активные ID; транзакция проверяет владельца, удаляет избранное и связанные регистрации/занятость события, а медиа удаляет backend с lease и безопасным повтором. UI показывает удаление только для серверно подтверждённых ID и запрашивает подтверждение. ## Первичный профиль: заявка с подтверждением школы

Серверный Яндекс ID flow выпускает сессию, но не назначает роль. Неизвестная личность может отправить заявку с именем, классом и одной из двух школ в серверном каталоге; клиент не может добавлять школы или передавать роль. Пока заявка ожидает решения, `fam_user_profiles` не создаётся. Очередь видит только школьный администратор своей школы; подтвердить/отклонить заявку может администратор той же школы, а одобрение всегда создаёт профиль с ролью `student`. При решении имя/класс очищаются из заявки, одобренные данные переносятся в профиль. API, интерфейс и синтетический end-to-end сценарий с межшкольными отказами проверены в CI и на одноразовой YDB.

При повторном входе заявитель может получить только собственные `request_id`, школу, статус и дату заявки. Имена, класс и внешний subject не попадают в этот ответ. Активную заявку UI не предлагает дублировать; после одобрения можно проверить профиль повторно, а после отказа — подать новую заявку. Сценарий статусов `pending` → `approved` проверен на синтетической YDB.

Пользователь с активным профилем может изменить только собственные имя, фамилию и класс через отдельный `PATCH /api/v1/me`. Сервер проверяет вход и формат полей, а YDB обновляет только три разрешённых поля по issuer/subject текущей сессии. Поля роли, школы и user id из запроса игнорируются; интерфейс показывает имена школьным администраторам согласно назначению исходного FAM.

Для ученика с уже одобренным школьным профилем добавлен отдельный запрос роли `council_member` или `school_admin`. Очередь ограничена школой; администратор должен закрепить заявку за собой, а завершить решение может только он же. Одобрение меняет роль в профиле и атомарно пишет запись аудита без внешнего subject или персональных полей. До реального использования нужно отдельно проверить соответствие исходному email-подтверждению: текущий Yandex ID адаптер не предоставляет эквивалент `email_confirmed_at`, поэтому доступ к заявке основан на уже одобренном школой профиле и последующем решении администратора.

Ограничения до любого реального тестирования: список содержит только две школы, найденные в текущем UI, полный перечень не подтверждён; ожидающие имя и класс автоматически удаляются YDB по TTL `P30D` от `created_at`. Очистка фонова́я, её точное время не гарантировано; удаление из резервных копий и реальная процедура удаления/обжалования пока не проверены. Реальный OAuth, школьную идентификацию, согласия и правовую основу не проверяли.

## Последовательность бесплатного переноса

1. Отделить российскую копию интерфейса и заменить Supabase URL/SDK на конфигурацию отдельного backend.
2. Перенести схему в YDB, сохранив ограничения доступа и транзакционные инварианты; проверять миграции на локальной/эфемерной среде без пользовательских данных.
3. Перенести функции в совместимые Node.js endpoints, затем подключить YDB репозитории и российское S3 API.
4. Выбрать бесплатные Auth, вычисления и расписания. Не включать подписки, платные trial, выделенные узлы, домены или ресурсы с тарификацией.
5. Прогнать проверки безопасности и интеграционные тесты на пустых синтетических данных. Реальные пользователи и школьные данные не подключаются до отдельного допуска.
