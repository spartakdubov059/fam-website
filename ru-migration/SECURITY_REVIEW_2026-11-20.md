# Ручная проверка безопасности FAM RU — 20 ноября 2026

## Исправление свежей аутентификации для чувствительных действий (20 ноября 2026)

Ранее `force_confirm=yes` из Яндекс OAuth превращался в локальный `step_up_confirmed_at` и принимался как свежая аутентификация. Документация Яндекса определяет `force_confirm` как повторный запрос согласия и выбор аккаунта, без утверждения о повторном вводе учётных данных ([описание параметра](https://www.yandex.ru/dev/id/doc/ru/codes/code-url)). Такое поведение нельзя использовать как доказательство `auth_time`.

В кодовой ревизии [170a0ef](https://github.com/spartakdubov059/fam-website/commit/170a0ef9a3ef7e5ea107c6ee7e989f3f32decb13) и проверенной ревизии [0d41c98](https://github.com/spartakdubov059/fam-website/commit/0d41c9824a8c38416e13879d8ad73f0e64ab1440) общая проверка принимает только provider-asserted `authenticated_at` из проверенного OIDC `auth_time`. Яндекс consent/session timestamp удалён из этого пути. Для обычной Yandex ID cookie-сессии удаления, школьные блокировки и другие операции, требующие свежей аутентификации, отвечают отказом; UI больше не предлагает повторное согласие как способ пройти gate.

Локально на Node 22 прошли `362/362` backend-теста. Точные [SDK/Sharp CI #44770366256](https://github.com/spartakdubov059/fam-website/actions/runs/44770366256) и [disposable YDB CI #44770366230](https://github.com/spartakdubov059/fam-website/actions/runs/44770366230) завершились успешно. Эти проверки не являются полным security sign-off, не проверяют реальный OAuth или российское облако. Текущий managed diff scan не стартовал: Codex Security вернул `Review changes requires a non-bare Git worktree with a resolvable HEAD`; scanId и формальный отчёт не созданы. До включения чувствительных операций нужен провайдерский фактор с проверяемым временем аутентификации или другой независимый сильный фактор; пока ограничения намеренно остаются.

## Дополнение: срок хранения сообщений в очереди проверки (20 ноября 2026)

До staging нужен утверждённый срок хранения и разрешение на соответствующее правило удаления. Пока это остаётся незакрытым вопросом приватности и потенциального расхода квоты.

## Объём проверки

Первичный ручной обзор был выполнен на коммите `047a5e1d844034705b212a4c0533fb6b8a999d59`. Повторно проверена изолированная ветка `migration/yandex-cloud` на commit `cf628fef557701e81d1d9cd06462c4f7fc1f9dd3`, включая CSP hardening. Обзор охватывает:

- Яндекс ID OAuth/PKCE, подпись и сроки действия cookie, проверку профиля OAuth и обработчик выхода.
- Проверку OIDC bearer JWT и JWKS, а также загрузку роли и школы из профиля YDB.
- Общую диспетчеризацию HTTP API, отказ при ненастроенных адаптерах и нормализацию пути статических файлов.
- Маршруты приватных фото объявлений, аватаров и идей: проверку роли/школы, приватное кеширование, ограничения размера загрузки и проверку результата обработки Sharp.
- Выборочные транзакции YDB для школьной роли, фото, safety-сигналов и удаления аккаунта. Значения передаются через параметризованные tagged templates.

Для чувствительных операций обычное время создания сессии не считается временем аутентификации. Проверяется недавний OIDC `auth_time` либо подписанное подтверждение намерения, возникшее только после соответствующего OAuth state с `force_confirm=yes`. Это подтверждение намерения не доказывает повторный ввод пароля или свежую аутентификацию у провайдера; интерфейс описывает его как подтверждение действия через Яндекс ID.

На снимке `047a5e1` был подтверждён дефект средней серьёзности: очистка safety-сигналов зависела от открытия очереди, а прямые идентификаторы могли сохраняться более 90 дней. В ветке добавлена схема `31_safety_incident_ttl.yql` с TTL 90 дней. YDB CI на `101faf22` успешно применила схемы 01–31 и прошла синтетические интеграционные сценарии. TTL удаляет записи фоново и не гарантирует точный момент удаления; идентификаторы могут оставаться до 90 дней. Допустимость срока и обработки данных после удаления аккаунта требует утверждённой политики для реального запуска. [YDB TTL](https://ydb.tech/docs/en/concepts/ttl)

При повторной проверке CSP найдено, что `script-src 'unsafe-inline'` разрешал выполнение любого inline JavaScript и ослаблял защиту при возможной XSS. В commit `e70b6fb` bootstrap вынесен в `app/web/shell-bootstrap.js`, а `script-src` ограничен `'self'`. В `cf628fe` встроенный CSS вынесен в `app/web/shell.css`; `style-src` тоже ограничен `'self'`. В HTML нет inline-атрибутов `style` и встроенных `<script>`/`<style>`. Текущие тесты проверяют same-origin загрузку обоих файлов и применение CSP. Это hardening меры защиты, а не подтверждение найденной XSS.

Остальные просмотренные участки не дали подтверждённых дефектов. Это результат ограниченного ручного просмотра, а не полный аудит кода или разрешение к развёртыванию.

## Дополнение: проверка audience в bearer OIDC (20 ноября 2026)

В `auth/oidc-bearer.mjs` валидатор принимал JWT, если `aud` содержал настроенную аудиторию, даже когда claim перечислял и другие приложения; присутствующий `azp` не сверялся с клиентом. Кроме того, он не требовал обязательный `iat` и пропускал его будущее значение. Для этой установки нет allowlist дополнительных доверенных audiences, поэтому такой токен не должен приниматься как предназначенный только FAM RU. Валидатор теперь допускает ровно одну аудиторию FAM RU (строку или одноэлементный массив), требует `iat` не позже 5 секунд от текущего времени и, если `azp` задан, требует совпадения. Это следует проверкам audience, `iat` и authorized party из [OpenID Connect Core, раздел 3.1.3.7](https://openid.net/specs/openid-connect-core-1_0.html#IDTokenValidation).

Синтетические тесты покрывают одноэлементную аудиторию, совпадающий `azp`, лишнюю аудиторию, несовпадающий `azp`, отсутствие `iat` и время выпуска в будущем; полный локальный backend suite — **389/389**. Неизвестно, выдаёт ли будущий настроенный российский OIDC issuer multi-audience tokens: облачная конфигурация не подключена. Такое поведение намеренно закрыто по умолчанию; при необходимости нескольких доверенных audiences их потребуется явно задать и тестировать. Управляемый Standard scan не дал результатов: запуск workbench завершился timeout после 300 секунд, scan ID не был возвращён. Это локальное hardening и проверка, не полный независимый security sign-off.
