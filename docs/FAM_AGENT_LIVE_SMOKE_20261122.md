# FAM — реальная проба автономной цепочки (22 ноября 2026)

## Назначение

Это разовая контролируемая проверка системы: закрытая очередь Supabase → `fam-agent-coder-bridge` → локальная Qwen 3.8 в GitHub Actions → независимые тесты → Pull Request только при доказанном исправлении → решение владельца.

Само добавление этого файла в `main` вызывает `fam-codex-developer.yml` через уже существующий `on.push.paths: docs/**`. Это не изменяет интерфейс сайта, базу, модерацию или права школьников.

## Единственное тестовое задание

- Проба записана в приватную очередь `private.fam_agent_tasks`, тип `technical / coder_patch_request`.
- `task_key: audit_accessibility` — проверить доступность публичного интерфейса, клавиатурную навигацию, подписи элементов и фокус.
- `event_code: js_runtime`, `page_area: other`, `occurrences: 0` — это технические поля фиксированного протокола. **Никакой реальный сбой не утверждается**.
- `source: system`, `approval_required: false` относится лишь к разрешению передать задачу анализатору, не к одобрению изменения кода.
- Одна попытка: `max_attempts: 1`; нет ID школьников, сообщений, URL запросов, логов или секретов.

## Критерии приёмки

1. GitHub Actions реально запустился после merge этого документа; не считать PR-only тест заменой main-run.
2. Защищённый bridge вернул одно разрешённое задание, а не приватные данные, `claimed=true`. При отсутствии GitHub secrets, 401/403, ошибке сети или отсутствии задачи — фиксировать конкретное состояние, не выдумывать успех.
3. Qwen 3.8 выполнила локальный анализ. **Без подтверждённого дефекта правильный результат — `no_patch`**, а не вымышленное исправление.
4. Если patch создан, он должен успешно пройти `git apply --check`, allowlist, независимые security/moderation/UI тесты и открыться как отдельный PR без merge.
5. В Supabase задание переходит в `completed/failed/blocked` с техническим итогом; после генерации статус `model_completed` **не равен** успешной независимой QA или готовому production.
6. Control Tower читает только шесть агрегатов очереди. Сообщения, профили, детали задач и токены в отчёт не уходят.
7. Ни одна модель не публикует изменения автоматически. Сайт и пользовательские данные остаются без изменений.

## Улучшения стабильности (следующая итерация)

- P0: **Lease/таймаут** — сейчас аренда задания максимум 7200 секунд, а job генерации может выполняться 180 минут. Добавить узкий heartbeat/renew с ограничениями, чтобы длительная корректная работа не превращалась в ложный сбой.
- P0: **Этапы результата** — разделить `model_generated`, `qa_passed`, `pr_created`, `awaiting_owner`, `merged`, `postmerge_verified`. Нельзя помечать исправленным до независимой QA и PR.
- P0: **Никаких выдуманных задач** — запуск только по подтверждённому сигналу или вручную согласованному техническому тесту; источники и доказательства сохраняются в служебном аудите.
- P1: **Контракт задания** — явная цель, затрагиваемые пути, доказательства из безопасных агрегатов, критерии приёмки, требуемые тесты, уровень риска, ответственный, инструкция отката; никаких произвольных текстов школьников.
- P1: **Отдельный read-only токен** для `health`, не разделяемый с `claim/finish`. Доступ только из main, секреты не передавать в ИИ.
- P1: **Точечные контрольные метрики** — доля успешных генераций, QA pass rate, p95 выполнения, число просроченных lease, стоимость runner-минут, частота необоснованных patches.
- P2: **Экономия бесплатных лимитов** — дешёвый preflight до загрузки 27B, кэш весов, повторные запуски только при обоснованном коде сбоя и backoff вместо бесконечных циклов.
- P2: **Канареечное внедрение** — изменения из PR только после approval и postmerge-проверки, автоматическая сигнализация при регрессии без произвольного rollback/SQL.

Этот файл — техническое свидетельство намеренного контролируемого запуска, а не отчёт об успешном завершении.
