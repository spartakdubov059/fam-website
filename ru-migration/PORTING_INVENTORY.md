# Инвентаризация переноса FAM RU

Обследование исходников ветки `migration/yandex-cloud`, 13 ноября 2026. Это перечень компонентов для самостоятельного переноса по коду текущего FAM; архив предыдущей сборки не требуется для этого этапа.

## Объём исходного приложения

- Статический фронтенд в корневом `index.html`; сейчас он обращается к Supabase напрямую.
- 7 Edge Functions: `council-management`, `fam-agent-coder-bridge`, `fam-agent-worker`, `fam-listing-image-worker`, `moderate`, `school-admin-access`, `submit-content`.
- 69 SQL migration-файлов. Их нужно переносить и проверять последовательно, с аудитом RLS, RPC, триггеров, приватных схем и расширений.
- 7 расписаний `pg_cron`; на российской копии их надо заменить управляемыми задачами только после проверки бесплатного способа запуска и повторов.
- Зависимости, которые нельзя потерять: Auth и роли, приватные/публичные медиа, модерация, очереди, учёт событий, удаление аккаунта, школьные ограничения доступа и фоновые отчёты.

## Перенесено в изолированный backend

- Частичные пользовательские сценарии: публичная доска объявлений с избранным и событиями, подача объявления с состоянием `pending` и фото, отправка школьных идей, школьная модерация текста/фото/заявок на события. API, UI личных сообщений и обращение автору активного объявления подключены; получатель берётся сервером из объявления, сообщения ограничены школой и проходят проверку. Служба модерации сообщений не сконфигурирована, поэтому запись fail closed. Личный кабинет и большая часть школьских интерфейсов ещё не перенесены.
- Добавлен модуль API записи на мероприятия: уникальная запись пользователя, транзакционная проверка ограниченной вместимости, отмена участником, счётчик мест без раскрытия записавшихся и решение по заявке владельцем мероприятия с проверкой роли и школы.
- Гостевая доска показывает детали мероприятия и поддерживает вход, запись, отмену своей записи. Backend позволяет школьным администраторам и совету просматривать минимальные данные заявок только по своей школе; экран школьной модерации подключён: сотрудники школы видят очередь ожидающих заявок и могут подтвердить или отклонить их; список ограничен школой и содержит только имя и класс заявителя. Схема проверена на одноразовой YDB в CI, но остаётся тестовой: перед облачным запуском нужны отдельная миграция базы и бесплатное окружение с контролем расходов.
- Приватный API загрузки фотографий подключён к форме российского UI: принимает ограниченные типы и размер, нормализует файл в WebP и сохраняет его по серверному ключу в приватном S3-совместимом бакете. Ключ связывается с pending-объявлением; при ошибке отправки UI просит сервер удалить ещё не привязанный объект, а backend отказывает в удалении объекта, уже используемого объявлением. Школьный модератор видит в same-origin очереди только pending-объявления своей школы и может одобрить фото перед публикацией объявления. Публичный UI отображает только одобренное фото активного объявления через серверный маршрут. Проверены межшкольные запреты, передача бинарных данных, UI очереди и удаление незакреплённого объекта. Периодический сбор файлов после закрытия вкладки остаётся не реализован; до отдельного тестового облачного окружения и лимитов хранения подключать реальные аккаунты нельзя.
- Для брошенных загрузок добавлен реестр `fam_pending_media`, атомарная привязка к объявлению и CLI-сборщик. До удаления YDB выдаёт lease для неподвязанных файлов старше 7 дней; привязанные файлы исключаются, неудачные удаления могут повторяться после lease. Жизненный цикл проверен на одноразовой YDB в CI; автоматический запуск/cron не включён.
- Добавлено удаление собственного активного объявления для роли `student`: закрытый endpoint выдаёт пользователю только его активные ID; транзакция проверяет владельца, удаляет избранное и связанные регистрации/занятость события, а медиа удаляет backend с lease и безопасным повтором. UI показывает удаление только для серверно подтверждённых ID и запрашивает подтверждение. На commit `13a1aa7b3d4f7577bd8f111202039a69a79f11b9` CI прошёл 142 backend-теста и одноразовую YDB интеграцию на синтетических данных.
- Добавлена схема учёта временных ограничений с сохранением нескольких событий для пользователя. Общий backend-барьер блокирует авторизованные записи через API объявлений и медиа при активном ограничении и отказывает с 503, если статус нельзя проверить; чтение остаётся доступным. Локальный YDB integration workflow проверяет синтетическую блокировку и чтение. Выдача/снятие ограничений администратором, повторная аутентификация для чувствительных действий, журнал аудита и интерфейс управления остаются неперенесёнными.

## Первичный профиль: заявка с подтверждением школы

Серверный Яндекс ID flow выпускает сессию, но не назначает роль. Неизвестная личность может отправить заявку с именем, классом и одной из двух школ в серверном каталоге; клиент не может добавлять школы или передавать роль. Пока заявка ожидает решения, `fam_user_profiles` не создаётся. Очередь видит только школьный администратор своей школы; подтвердить/отклонить заявку может администратор той же школы, а одобрение всегда создаёт профиль с ролью `student`. При решении имя/класс очищаются из заявки, одобренные данные переносятся в профиль. API, интерфейс и синтетический end-to-end сценарий с межшкольными отказами проверены в CI и на одноразовой YDB.

При повторном входе заявитель может получить только собственные `request_id`, школу, статус и дату заявки. Имена, класс и внешний subject не попадают в этот ответ. Активную заявку UI не предлагает дублировать; после одобрения можно проверить профиль повторно, а после отказа — подать новую заявку. Сценарий статусов `pending` → `approved` проверен на синтетической YDB.

Пользователь с активным профилем может изменить только собственные имя, фамилию и класс через отдельный `PATCH /api/v1/me`. Сервер проверяет вход и формат полей, а YDB обновляет только три разрешённых поля по issuer/subject текущей сессии. Поля роли, школы и user id из запроса игнорируются; интерфейс показывает имена школьным администраторам согласно назначению исходного FAM.

Для ученика с уже одобренным школьным профилем добавлен отдельный запрос роли `council_member` или `school_admin`. Очередь ограничена школой; администратор должен закрепить заявку за собой, а завершить решение может только он же. Одобрение меняет роль в профиле и атомарно пишет запись аудита без внешнего subject или персональных полей. До реального использования нужно отдельно проверить соответствие исходному email-подтверждению: текущий Yandex ID адаптер не предоставляет эквивалент `email_confirmed_at`, поэтому доступ к заявке основан на уже одобренном школой профиле и последующем решении администратора.

Ограничения до любого реального тестирования: список содержит только две школы, найденные в текущем UI, полный перечень не подтверждён; ожидающие имя и класс автоматически удаляются YDB по TTL `P30D` от `created_at`. Очистка фонова́я, её точное время не гарантировано; удаление из резервных копий и реальная процедура удаления/обжалования пока не проверены. Реальный OAuth, школьную идентификацию, согласия и правовую основу не проверяли.

## Последовательность бесплатного переноса

1. Отделить российскую копию интерфейса и заменить Supabase URL/SDK на конфигурацию отдельного backend.
2. Перенести схему в YDB, сохранив ограничения доступа и транзакционные инварианты; проверять миграции на локальной/эфемерной среде без пользовательских данных.
3. Перенести функции в совместимые Node.js endpoints, затем подключить YDB репозитории и российское S3 API.
4. Выбрать бесплатные Auth, вычисления и расписания. Не включать подписки, платные trial, выделенные узлы, домены или ресурсы с тарификацией.
5. Прогнать проверки безопасности и интеграционные тесты на пустых синтетических данных. Реальные пользователи и школьные данные не подключаются до отдельного допуска.

## Ограничения

Эта инвентаризация не является готовой миграцией и не утверждает совместимость YDB или объектного хранилища. Успешный SDK smoke test проверяет только импорты/API и локальную обработку изображения. До реализации и бесплатного тестового окружения staging остаётся выключенным. Если бесплатный сервис не обеспечивает нужную надёжность или безопасность, соответствующий этап остаётся заблокированным.
