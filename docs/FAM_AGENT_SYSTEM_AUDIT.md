# Аудит агентной системы FAM

Дата проверки: 13 ноября 2026 года. Проверены репозиторий, GitHub Actions и живой Supabase проект `tfacqpljrvfpcrhdovbu`. В production выполнялись только чтение миграций, агрегированных статусов очереди, расписаний и последних запусков.

## Проверенные факты

- Supabase проект активен, регион `eu-central-1`, PostgreSQL 17.11. В актуальной истории миграций присутствуют queue bridge, retry recovery, producer schedule и cron retry reaper.
- Активны функции `fam-agent-worker` v17 и `fam-agent-coder-bridge` v1; bridge отвечает за узкое claim/finish API, но не выполняет модель сам.
- Семь расписаний FAM активны. На момент снимка последние доступные исполнения каждого из них были `succeeded`; Worker — каждые 5 минут, аудит ошибок сайта — каждый час, producer coder — ежедневно.
- Production queue содержит 76 задач: 73 `completed`, 3 `failed`. Для `coder_patch_request`: 1 `completed`, 3 `failed`. Запрашивались только сгруппированные количества, без payload/описаний.
- GitHub Actions run [#43362562139](https://github.com/spartakdubov059/fam-website/actions/runs/43362562139) завершился зелёным как запуск инфраструктуры модели, но Queue claim сообщил `No queued coder task`; поэтому `verify` и `prepare_review` были пропущены. Это не подтверждает создание patch или PR.
- Открытые PR #65 (точные операции редактирования) и #64 (Mellum) основаны на более ранней версии `main`; PR #65 проверен как mergeable и содержит аудиторскую таблицу, exact-edit helper, unit tests и изолированную проверку отказа QA. Обязательный CI на актуальном PR head `9c9ef091` завершился успешно; deliberately failing patch был отклонён. Два отдельные smoke workflows других моделей удалены из diff, основной контур остаётся на Qwen.
- Supabase security advisor сообщает об установленном в `public` расширении `pg_net` и публичном SECURITY DEFINER RPC `report_fam_site_error`; требуется отдельная проверка его намеренной анонимной телеметрии и минимальности прав. Это не исправляется в рамках аудита без разбора миграции и без безопасного способа обновить advisor findings.
- GitHub ruleset «FAM — защита main» активен и не имеет bypass actors, но `required_approving_review_count=0`. Следовательно, правила защищают прямые push и требуют PR/status check, однако сами по себе не доказывают одобрение владельцем.

## Следующий безопасный этап

1. Проверить Qwen на безопасном synthetic задании без личных данных; workflow #49 не получил задачу из очереди и поэтому не подтверждает создание patch.
2. Проверить полный путь только в отдельной ветке/PR: synthetic task → patch → независимый QA → reviewer report → открытый PR. Подтвердить, что намеренно нерабочий patch блокируется, а корректный оставляет PR открытым.
3. Не объединять PR и не публиковать production. Для запуска Qwen из очереди должно быть доказано, что он выбрал только разрешённый task и не получает приватный payload.
4. Отдельно оценить серверную обязательность подтверждения владельцем и advisories Supabase; не применять миграции и не менять Auth/RLS/производственные данные в этой фазе.
