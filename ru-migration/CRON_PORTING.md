## Ручная сводка по RU очередям отчётов

Оператор может выполнить `node ru-migration/app/backend/check-background-queues.mjs` в уже настроенной конфигурации RU backend. Команда читает агрегированные статусы из очередей отчётов и allowlisted `fam_agent_tasks`: ожидание, захват, завершение, блокировки/ошибки за 24 часа, просроченные lease и возраст самой старой записи. Она не читает payload, сводки, текст, идентификаторы пользователей или сообщения; таймер не создаётся. Общая очередь ограничена четырьмя служебными типами и не эквивалентна произвольным задачам исходной `fam_agent_tasks` или пользовательским очередям модерации.

## Безопасная очистка загрузок

Российский backend содержит реестр `fam_pending_media` и CLI `ru-migration/app/backend/cleanup-pending-media.mjs`: он удаляет только неподвязанные загрузки старше семи дней, предварительно получив для каждой lease в YDB. Школьный отчёт запускается в 03:30 UTC (06:30 MSK), digest оркестратора — в 04:00 UTC (07:00 MSK), readiness — в 03:40 UTC (06:40 MSK), site-error digest — каждый час в `:30` UTC; cleanup запускается раз в 6 часов. Новый безопасный worker подготовлен каждые пять минут без catch-up после простоя. Повторное расписание systemd отдельно вызывает agent report, readiness и очистку; Yandex Timer делает отдельные вызовы сразу. Поскольку Yandex Timer допускает параллельные вызовы, очередь обеспечивает детерминированный ID на `(тип задачи, UTC-слот)`, эксклюзивный claim и lease-bound завершение: повторный trigger для того же слота не создаёт второй safe-task. Это проверено unit и точным disposable YDB CI [#45221304505](https://github.com/spartakdubov059/fam-website/actions/runs/45221304505) на code commit `98fffa6`: synthetic enqueue/claim/finish для 03:40, 04:00 и `:30` UTC, отрицательные проверки неверных слотов; одноразовая база удалена. Это не проверка доставки реального Yandex Timer. Все timers не установлены и не включены: бесплатная среда не настроена. RU coder producer перенесён только как безопасная постановка агрегированной ручной проверки; bridge не запускает Qwen/модель/инструменты, а тип задачи исключён из автоматического allowlist и остаётся в очереди. Image worker заменён ручной проверкой; RU system health проверяет доступность обязательных таблиц RU-схемы без чтения строк, агрегат очередей и локальные timers, но не права записи/ACL YDB и не полный исходный аудит PostgreSQL прав/расширений.

`fam-ru-pending-media-cleanup.timer` — дополнительное внутреннее задание RU, а не перенос upstream cron: оно запускает ограниченную очистку каждые шесть часов в `00,06,12,18:17 UTC`. `fam-ru-agent-daily-report.timer` сохранён только как исторический файл и не предназначен для установки: исходное глобальное расписание отменено и заменено школьным отчётом и агрегированным digest. CI исключает этот файл из installable inventory и проверяет явную пометку `do not install or enable`; runtime health также не требует его. В папке восемь timer-файлов: семь проверяемых (шесть ограниченных аналогов активных upstream cron, включая изменённую частоту проверки ошибок, и одно локальное задание очистки), плюс один исторический файл. Установочные действия остаются отключёнными.

## Условия переноса

- Реализовать каждую процедуру на российском backend и явно закрепить идемпотентность, блокировки, повторы и журналирование.
- Заменить прямой вызов Supabase Edge Function внутренним российским обработчиком после переноса и проверки очереди изображений.
- Рассчитать расписания в UTC, отдельно документировать нужное московское время.
- До полного переноса всех обработчиков оставить задания выключенными. Не добавлять облачные cron-сервисы, платные функции или тестовые вызовы исходных production URL.
- Запускать только в одноразовом окружении и на синтетических данных; провайдерские задания по отчётам и агентам могут обращаться к внешним моделям и отдельно требуют проверки отсутствия расходов.

## Read-only проверка состояния systemd (20 ноября 2026)

Команда `npm run check:timers` проверяет фиксированный список установленных RU timer units через `systemctl show` и `systemctl is-enabled`. Для каждого используемого расписания она также проверяет результат последнего запуска парной службы и свежесть запуска (26 часов для суточных задач, 12 минут для worker timer раз в 5 минут, 7 часов для очистки медиа, 2 часа для ежечасной сводки). В вывод попадают только имена ожидаемых таймеров и булевы признаки; timestamps, журналы и данные пользователей не выводятся. Команда ничего не устанавливает и не включает. До установки службы ожидаемо возвращает ненулевой код; в macOS окружении разработки без systemd это также безопасный fail-closed результат. Структурная проверка `compat/verify-systemd-timers.mjs` сверяет точный набор всех восьми файлов-таймеров, сервисные ссылки, критичные `Persistent=false` и ожидаемые календарные выражения; полную проверку systemd делает Linux CI.
