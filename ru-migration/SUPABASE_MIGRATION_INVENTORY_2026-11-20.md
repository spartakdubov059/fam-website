### Core access policy review (2026-11-20)

Migration `20261108001537_harden_fam_core_access_policies.sql` was compared with the current RU routes and repository projections. Evidence: `auth/database-actor.mjs` derives the actor only from verified issuer+subject and requires an active profile; `listings-api.mjs` uses that actor for listing, ideas, messages and registrations; `ydb-listings.mjs` binds user/school IDs and returns bounded projections. `claim_admin_role` has no RU endpoint; role changes use school-scoped review flows. The RU client has no direct YDB table connection, so access is enforced in the backend.

22 ноября проверка recipient read-receipt выявила, что `UPDATE fam_messages` фильтровался только по message ID; теперь сам `UPDATE` и подтверждение результата содержат `receiver_id` и `school_id`. Аудит event registrations также выявил, что репозиторий блокировал модерацию школьными администраторами, пропущенную API. Commit [`6527fe6`](https://github.com/spartakdubov059/fam-website/commit/6527fe60f12f1a9e861ea2fb979bc6137cba1a6b) восстановил доступ организатора только к собственному событию и same-school review для активных `school_admin`/`council_member`; SQL заново проверяет владельца и профиль, а список заявок ограничен владельцем либо активной ролью в той же школе. Тесты: `listings-api.test.mjs`, `ydb-listings.test.mjs`; backend suite **439/439** локально, [SDK/Sharp CI #44962759676](https://github.com/spartakdubov059/fam-website/actions/runs/44962759676), [synthetic YDB CI #44962759592](https://github.com/spartakdubov059/fam-website/actions/runs/44962759592). Runtime IAM и полный response-field matrix остаются непроверенными.

- Source profile: own-profile route rather than direct column grants; source role remains server-assigned. RU profile onboarding/update uses actor-bound API and role-review flows.
- Source listings: active rows are public; own listing operations and moderation are server-side. Existing RU tests cover pending listings hidden from public reads and school-bound moderation.
- Source messages: RU reads bind current user as sender/recipient and school; writes use verified actor, same-school recipient checks, durable quota and moderation paths.
- Source ideas: RU binds uploader and school and limits review to same-school staff; own deletion and staff review are explicit API operations.
- Source registrations: see event occupancy/cancellation review below.
- Registration access: RU applicant reads are constrained to the event school and active event; rows are visible to the event owner or an active same-school `school_admin`/`council_member`. Registration decisions recheck the active actor profile and same-school event inside the YDB transaction, then require the actor to be the event owner or hold one of those school roles. ### Account deletion and recovery workflow
