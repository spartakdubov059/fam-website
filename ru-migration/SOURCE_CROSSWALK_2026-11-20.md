# Сверка FAM `main` и RU-ветки

## Дополнительная сверка актуального `main` — 22 ноября 2026

Текущий source `main` (`6ae3b2fb4fd175d6d52bfeeab2eb6611fce6fd51`) сравнен с текущей удалённой RU-веткой `migration/yandex-cloud` (`7f921c1c9b26846727820324a57ed94f63290218`). В полном diff из 337 файлов эта изолированная ветка, созданная до дальнейшей основной разработки, ожидаемо не содержит более поздние изменения сайта и содержит российский runtime, которого нет в `main`. Такой diff нельзя сливать целиком: он затронул бы production-конфигурацию и удалил бы миграционные материалы. Поэтому ниже отражён только последний отдельный upstream-коммит по backend-поведению; остальные переносимые изменения интерфейса требуют отдельной выборочной сверки.

Отдельная проверка интерфейса текущего `main`: school announcements, polls, открытые события и показ событий в верхней карусели уже имеют независимый RU UI в `ru-migration/app/web/pulse.js`, `public-board.js`, `shell-bootstrap.js` и `hero-carousel.js`, а данные читаются через YDB API `/api/v1/pulse`. Поэтому поздние `school-pulse.js` и `school-pulse.css` из `main` привязаны к Supabase RPC и не переносятся в российскую оболочку. Доказательством являются существующие RU маршруты и UI компоненты; актуальная браузерная визуальная проверка не выполнялась. Более новые изменения `main` в `index.html`, доменных адресах, Netlify workflows и общих агентах не включаются автоматически: их нужно оценивать отдельно, чтобы не перенести production endpoint или секретную конфигурацию.

В текущем `main` пользователь меняет email через Supabase Auth с подтверждением нового адреса. RU-профиль не хранит email и не может менять адрес у Яндекс ID; вместо этого настройки профиля ведут в аккаунт Яндекс ID и объясняют, что FAM использует адрес только для одноразовых кодов. Регрессионный UI-тест проверяет эту ссылку и отсутствие хранения email в профиле. Это замена на управление у провайдера, а не точное совпадение потока Supabase; реальный аккаунт и обновление адреса в OAuth не проверялись.

Независимая перепроверка текущего кода на Node `22.15.0` прошла `464/464` backend tests после повторной установки lockfile-зависимостей; `npm audit` сообщил ноль уязвимостей для backend и SDK/Sharp. `compat/verify.mjs` вывел `SDK_COMPAT_PASS`, переносимый парсер проверил 7 устанавливаемых таймеров. Пакет Cloud Function собран и проверен ZIP-тестом: 134 файла, runtime `nodejs22`, SHA-256 `d1073a4287a9d9d94b5c8562fe90f6f8d2f4037570f76fc55101e74a19b9cb17`. PR #137 (`69bdac0`) имеет успешные YDB и SDK/Sharp workflows. PR #138 (`8137b01`) пока не имеет GitHub Actions runs; его локальный suite пройден, но YDB integration для новых изменений не запускалась. Облачная интеграция также не выполнялась. Рабочая копия содержит обновление перехода для управления email в Яндекс ID и локальные правки расписания/документации; они не отправлялись в GitHub.

Эта сверка ограничена diff между указанными двумя ревизиями и не заменяет полный аудит всех миграций, SQL/RLS/RPC, функций и UI.

Сверка исходных изменений выполнена 20 ноября 2026. Проверенные указатели GitHub: FAM `main` `af1f0086066d18b3d814dd535f06eda733ae58de`; проверенная RU-ревизия кода `c3b90e2658802220984f4d3915828f6082f433fe`, текущая вершина ветки содержит последующие документальные записи. `main` не менялась этим переносом; RU-ветка изолирована. Эта таблица сохраняет исходный crosswalk девяти SQL-миграций и шести изменений функций; актуальная сверка всех семи Edge Function entrypoints и их отличий добавлена в [EDGE_FUNCTION_COVERAGE_2026-11-20.md](EDGE_FUNCTION_COVERAGE_2026-11-20.md). Это не построчная проверка всех последующих изменений `main`.

Старая российская ветка создана от исходной миграционной ветки, а не от нынешнего `main`. Между теми upstream-коммитами есть 9 новых SQL-миграций и 6 изменений Edge Functions. ## Что это означает

### Сверка клиентских итогов опросов (20 ноября 2026)

- В актуальной FAM `school-pulse.js` распределение ответов видно только проголосовавшему участнику или после закрытия опроса, и только при пяти и более голосах.
- RU API уже возвращал `counts` только от пяти голосов, но клиент показывал это распределение всем участникам открытого опроса. На локальной ветке `codex/fam-ru-port-next` исправлено: клиент соблюдает условие «проголосовал или опрос закрыт», проверяет целостность массива счётчиков и показывает процентное распределение. Добавлена регрессионная проверка для открытого, проголосовавшего и закрытого состояний.
- Исходный `fam_pulse_feed()` объединяет школьные объявления с активными мероприятиями без лимита мест. RU endpoint пропускал мероприятия из `fam_listings`; теперь он включает будущие/без даты open-entry мероприятия раньше объявлений, ограничивает описание 450 Unicode-символами и выдаёт только публичную проекцию без владельца и storage key. Добавлен synthetic YDB сценарий для open/capacity/expired событий.
- В upstream `school-pulse.js` гость видит общедоступные мероприятия без лимита мест даже без профиля школы. RU-shell раньше сразу предлагал вход; теперь для гостя используется существующий публичный `GET /api/v1/listings`, показываются максимум шесть активных мероприятий без лимита мест с будущей/неуказанной датой и только их открытые поля. Добавлена UI-регрессия для ограниченного и прошедшего события, обычного объявления и запроса без credentials.
- На локальной версии `ae22ff3` backend suite прошёл `346/346`; после гостевых мероприятий локально прошли `348/348` (включая недоступный public-feed fallback). SDK/Sharp verifier — `SDK_COMPAT_PASS`, portable timer parser проверил 8 файлов. Скрипт YDB integration прошёл syntax check, но само подключение к disposable YDB в этом окружении не запускалось; это не CI и не staging.

- Основные пользовательские сценарии этих 9 миграций представлены в RU-коде, но исходные Supabase-миграции нельзя применить к YDB. Остаётся отдельная работа по полноте соответствия всех 78 migrations, RPC, RLS, триггеров, семи Edge Functions, экранов и переходов.
- В RU-ветке источник upstream разделён: часть сценариев реализована, часть сознательно имеет безопасный ручной аналог из-за бесплатного лимита. Это не полная копия поведения `main` и не доказательство готовности для реальных пользователей.
- Российский staging не поднят: нет проверенной гарантии расхода 0 ₽, настроенных Yandex OAuth, YDB, S3, домена/хоста. Реальные аккаунты и данные учеников не использовались.
- До исправления отсутствующих звеньев, независимого security review и staging QA публикация и подключение реальных данных остаются закрыты.

## Обновление upstream от 20 ноября 2026

`main` продвинулась от `5e749c56` до `af1f0086` двумя коммитами. Перенос интерфейса FAM (#123, `5496264`) добавляет touch-навигацию, карточки Afisha для анонсов и опросов и показывает Afisha при пустых объявлениях. Этот UI-поток добавлен в RU: новости школы, опросы и карточки мероприятий находятся в общем адаптивном grid, мобильная навигация открывает Afisha и фильтрует список по событиям; см. [проверку Afisha](VALIDATION_2026-11-21_AFISHA.md). Это закрывает указанный layout-пробел, но не подтверждает полный UI/API parity. Новый workflow синхронизации production-доменов (`.github/workflows/fam-domain-sync.yml`) не переносится в российский staging, так как относится к production-доменам и не является пользовательской функцией FAM.
