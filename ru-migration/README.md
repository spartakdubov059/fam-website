# FAM RU — изолированная миграция на российскую инфраструктуру

**Рабочая ветка: `migration/yandex-cloud`. Не сливать в main и не развёртывать на production.**

Цель — подготовить российскую копию FAM отдельно от действующего сайта. Ветка `main`, текущий FAM, Netlify/Supabase и реальные данные учеников не используются для этих проверок.

## Подтверждено сейчас

- На commit `d50c900b7c9011589a61da5e7f0fab249e8899dd` прошли [138 backend-тестов на Node 22, установка закреплённых SDK и Sharp](https://github.com/spartakdubov059/fam-website/actions/runs/43517554535) и [интеграция на одноразовой локальной YDB](https://github.com/spartakdubov059/fam-website/actions/runs/43517554572). YDB прогон проверил регистрацию приватной загрузки, её атомарную связь с объявлением и очистку старого неподвязанного файла. Облачный staging не поднимался. Исторические 220 тестов из недоступного архива не подтверждены.
- Текущие локальные изменения дополнительно проверены на 142 backend-тестах (все пройдены на Node 24); это не заменяет обязательный прогон CI на закреплённом Node 22 и YDB, который будет создан после отправки изменений в эту ветку.
- Российский интерфейс включает публичную доску, избранное, события, личные сообщения, отправку объявлений/фото и идей, а также школьные очереди объявлений, фотографий, заявок на мероприятия и профили. Личные операции требуют настроенной авторизации и активного профиля в отдельной YDB.
- YDB зависимости backend зафиксированы точными версиями и lockfile.

## Что уже реализовано в изолированном коде

- Отдельная копия статического интерфейса в `app/web`.
- Fail-closed HTTP backend с API подачи объявления и школьной идеи; идеи без доступной проверки сохраняются только как `pending` и не входят в публичные чтения.
- Избранное подключено к публичной доске: вошедшие пользователи добавляют и удаляют активные объявления; гости переходят на Яндекс ID, а записи выполняются только от подтверждённого профиля.
- API и UI личных сообщений: с карточки можно обратиться к автору активного объявления; сервер сам определяет получателя и ограничивает его той же школой. Диалоги доступны только участнику. Пока провайдер модерации не подключён, текст fail closed и не записывается.
- OIDC bearer verification, разрешение ролей через профиль в YDB; дополнительно реализован серверный OAuth Яндекс ID с PKCE S256, одноразовой state-cookie, проверкой `client_id` профиля, часовым HttpOnly/SameSite cookie и logout. Для unsafe-запросов по cookie и logout требуется точное совпадение `Origin` с origin зарегистрированного callback.
- Маршрут школьной модерации объявления: права берутся из профиля YDB, решение ограничено школой объявления и переходом только из `pending`; используется транзакция YDB.
- Добавлен backend-модуль записи на мероприятия: открытые и ограниченные события, одно место на пользователя, транзакционная проверка вместимости, отмена своей записи, публичный счётчик без данных участников и решение владельца мероприятия с ролью школьного администратора/совета.
- Гостевая доска показывает дату и время мероприятия; пользователь может войти через Яндекс ID, записаться или отменить свою запись. Кнопки используют только same-origin запросы; HTML пользовательских полей не вставляется в DOM.
- YDB схема профилей и объявлений, параметризованный repository; добавлено публичное чтение только активных объявлений с ограниченным набором полей; `/api/v1/me` возвращает профиль из YDB только после проверки OIDC-токена.
- Локальные privacy/moderation gates; новые записи остаются `pending`, если проверка недоступна.
- Временные ограничения аккаунтов: отдельная таблица сохраняет события ограничения, а общий серверный барьер блокирует авторизованные записи в API объявлений и медиа при активном ограничении; при невозможности проверить статус запись отклоняется с 503. Чтение остаётся доступным. Схема и синтетический путь прошли одноразовую YDB интеграцию. Административная выдача/снятие ограничений, свежая повторная аутентификация, аудит действий и UI управления ещё не перенесены.
- При повторном входе незарегистрированный пользователь получает только собственный статус школьной заявки; endpoint не возвращает имя, класс или subject. Интерфейс не предлагает дублировать активную заявку и позволяет повторно проверить статус; после одобрения предлагает обновить сессию/страницу, а отклонённую заявку можно отправить заново. Полный цикл проверен синтетически.
- Ученик с одобренным школьным профилем может запросить одну из двух фиксированных ролей. Решение принимает администратор той же школы, который ранее закрепил заявку за собой; изменение профиля и три перехода заявки записываются в аудите без PII. Yandex ID не предоставляет проверенный эквивалент `email_confirmed_at`; поэтому текущий допуск основывается на уже одобренном школой профиле и решении администратора. Это отличие от исходной проверки email должно пройти отдельную оценку перед реальными пользователями.
- API приватной загрузки изображений: только активный профиль, JPEG/PNG/WebP до 5 МБ, проверка формата и преобразование Sharp в WebP, серверный случайный ключ с префиксом пользователя и приватный S3-совместимый объект с шифрованием на стороне хранилища. Без S3-конфигурации маршрут возвращает 503.
- Добавлены реестр загрузок `fam_pending_media` и одноразовый операторский сборщик `node cleanup-pending-media.mjs`: файлы связываются с объявлением атомарно, а очистка получает временную YDB-аренду и удаляет только неподвязанные загрузки старше 7 дней. При ошибке удаления аренда снимается либо истекает через 5 минут для повтора. Автоматическое расписание выключено; S3/YDB на российском сервере не подключались.
- Ученик может удалить только собственное активное объявление. API возвращает владельцу только его идентификаторы, а удаление проверяет роль и владельца, удаляет избранное и зависимые регистрации/счётчик события в транзакции. Медиа удаляется сервером по временной аренде; сбой хранилища оставляет ограниченную возможность повтора. Проверки добавлены локально; интеграционный CI для этой версии ожидается.
- Форма российской копии загружает фото через тот же backend, привязывает приватный ключ к новому объявлению и отправляет объявление на проверку. Если запись объявления не удалась, браузер запрашивает удаление ещё не связанного файла; backend проверяет владельца и отсутствие ссылки из объявления. Отдельная очередь модерации показывает pending-объявления только школьному администратору/совету школы из его профиля; фото можно проверить и принять до публикации объявления. Публичная доска показывает только одобренное фото активного объявления через same-origin маршрут с `image/webp`, `nosniff` и `private, no-store`. Межшкольный доступ проверяется тестами. Периодическая уборка файлов, оставшихся после закрытия вкладки или потери сети, ещё не реализована.
- Российская форма позволяет отправить школьную идею через защищённый API; при недоступной проверке идея сохраняется только как `pending`. В карточке объявления можно написать его автору; получатель определяется сервером по активному объявлению и разрешён только в той же школе. Вкладка сообщений загружает только собственные диалоги и позволяет отвечать. Маршруты защищены тестами, межшкольный запрет сообщений проверен на одноразовой YDB. Провайдер модерации текста не настроен: сообщения fail closed и не сохраняются до внешнего решения `ok`.

### Подключение Яндекс ID (пока не настроено)

Для отдельного тестового домена нужно зарегистрировать приложение Яндекс OAuth типа «Для авторизации пользователей», добавить HTTPS Redirect URI `https://<тестовый-домен>/auth/yandex/callback` и минимальное право `login:info`. В переменные окружения backend передаются `FAM_RU_YANDEX_CLIENT_ID`, `FAM_RU_YANDEX_REDIRECT_URI` и случайный `FAM_RU_SESSION_SECRET` длиной не менее 32 байт. Секреты не записывать в репозиторий или frontend. Для разработки допустим только `localhost` без HTTPS; удалённый адрес без HTTPS отклоняется.

Обмен кода и запрос профиля выполняются сервером. OAuth-токен не сохраняется и не передаётся в URL; браузеру выдаётся только подписанная краткоживущая HttpOnly cookie. Роли выдаются исключительно из `fam_user_profiles`; сам вход не создаёт профиль и не назначает роль. Для неизвестной личности доступна заявка на школьный профиль: каталог школ задан на сервере, пользователь не выбирает роль, новый профиль появляется только после решения администратора той же школы, и всегда получает роль `student`. Решение и приватные интеграционные сценарии проверены на синтетических данных в CI. Реальная регистрация OAuth-приложения и внешний вход не проверялись. Заявки на профиль настроены на YDB TTL `P30D` по `created_at`; истёкшие записи YDB удаляет в фоне, точный момент очистки не гарантируется. Резервные копии облачной базы не настроены и их удержание не проверено.

Эти части ещё не образуют полный перенос FAM. Требуются перенос и аудит всех исходных функций, SQL/RLS, ролей и фоновых задач, а также проверка всей пользовательской навигации и сценариев.

## Неподтверждённое / блокеры

- Архив `FAM_RU_Migration_Starter_2026-11-13_220tests.zip` в предыдущем чате дан временной ссылкой `sandbox:/mnt/data`, но вложения в истории нет и сам файл отсутствует в workspace. SHA архива и **220 тестов** независимо не воспроизведены. Текущий изменённый backend проходит 142 локальных теста под Node 24; закреплённый для проекта Node 22 и интеграция новой версии с одноразовой YDB ещё требуют CI.
- Реального российского облачного staging нет. Яндекс ID flow проверен только mock-тестами: нет зарегистрированного OAuth-приложения, redirect URI, активного профиля/онбординга и конфигурации backend. Облачные YDB, объектное хранилище, реальный OAuth, расходы и сетевые политики не проверялись.
- Семь исходных Edge Functions, 69 SQL миграций и расписания `pg_cron` перенесены не полностью; см. `PORTING_INVENTORY.md` и `CRON_PORTING.md`.
- Российский вход не готов для реальных пользователей: OAuth-приложение не зарегистрировано, а первичный доступ проверен только синтетически. Есть безопасная заявка на профиль, но каталог содержит только две школы, найденные в текущем UI; прежде чем расширять его, нужно подтвердить полный список. Перенесено изменение имени, фамилии и класса; аватары, удаление аккаунта и большая часть школьских панелей остаются неперенесёнными. UI сообщений есть, но работающая отправка зависит от ещё не подключённой службы модерации текста.
- Яндекс ID и российская база не настроены в реальном окружении. Поэтому экран записи и API проверены на синтетических данных в CI, но реальный вход пользователя пока невозможен.
- Никакие платные ресурсы и trial не запускались. У Yandex Cloud бесплатные объёмы ограничены месячными квотами: после их превышения начисляется плата. Бюджетные пороги только уведомляют и сами по себе не останавливают потребление. Поэтому при требовании строго 0 ₽ облачные ресурсы не создаём; используем только локальную эмуляцию, пока нет подтверждённого способа гарантировать отсутствие списаний. См. [Free tier](https://yandex.cloud/ru/docs/billing/concepts/serverless-free-tier) и [бюджеты](https://yandex.cloud/ru/docs/billing/concepts/budget).
