# FAM: PWA + фотогалерея (план реализации)

## Итог проверки текущего кода
- PWA: до этого не было web manifest, service worker и установки на домашний экран.
- Форма публикации сейчас принимает **одно** фото (поле `lImage`, `files[0]`).
- Бэкенд `submit-content` принимает `image_url`; публичная таблица `listings` имеет одно поле `image_url`.
- Фотография сначала попадает в приватный `listing-images-pending`, затем проходит проверку и только после одобрения появляется в публичном `listings-images`.
- Проверенные привилегированные роли могут обходить **ИИ-проверку изображения** по серверной роли/школе; остальные проходят стандартную модерацию. Ни одну из этих проверок нельзя обходить на клиенте.

## Этап 1: реализовано в этой ветке
- PWA с манифестом, фирменной иконкой, standalone display, относительными путями, подходящими для GitHub Pages и Netlify.
- Service worker кэширует **только фиксированные публичные статические ассеты**, не HTML, профили, чаты, API, объявления, аватары или изображения пользователей.
- Компонент `FAMGallery.photos` рендерит до пяти одобренных фотографий с защитой от неразрешённых URL, дублей и статусов модерации; старые объявления с одним `image_url` продолжают работать.
- Детальный просмотр поддерживает миниатюры и выбор основного фото. Карточки и фирменный дизайн сохранены.

## Этап 2: серверная загрузка 2–5 фотографий (нужна отдельная проверка перед выпуском)
1. Добавить модель `listing_photos` (или эквивалентную защищённую структуру) с `listing_id`, `owner_id`, порядком `position`, приватным `pending_path`, `public_url`, `review_status`. Проверить отдельные политики RLS: запись только владельцу, чтение публично только одобренных, сервисной очереди — по служебной роли.
2. Обновить `submit-content` на серверный приём массива **не более пяти** подписанных URL, с валидацией каждого URL, владельца, пути, типа, лимита и количества; не доверять `role`, `school_id`, `approved` из браузера.
3. Привязать изображения к объявлению, проверять каждое независимо в очереди и публиковать только после успешной проверки (или серверного bypass для действительной школьной роли с проверкой школы). Пока изображение не одобрено — хранить приватно.
4. При отказе в проверке показывать безопасный статус только по соответствующему фото, остальные одобренные оставить видимыми. При удалении объявления очищать приватные и публичные изображения без изменения чужих файлов.
5. В форме: `multiple` и лимит 5, локальные миниатюры, удаление выбранного файла, сортировка и отметка главного. Запрос с массивом отправлять только после обновления серверного API.
6. Миграция: существующие `listings.image_url` работают без изменений, а клиент принимает одобренные `image_urls` после их серверной выдачи. При использовании отдельной таблицы строить `image_urls` из записей с `review_status='approved'`, не из неконтролируемого пользовательского ввода.

## Обязательные проверки перед производственным релизом
- 0/1/2/5/6 файлов, дубли, неверный MIME, превышение размера, недействительные/просроченные ссылки.
- Нельзя загружать файл под чужим `user_id` или прикреплять к чужому объявлению; неподтверждённые фото никогда не попадают в публичный URL.
- Проверить роли админа, совета и обычного ученика, включая смену школы во время работы очереди.
- Проверить повторы запросов, очистку после ошибок, неограниченный рост хранилища и квоту модерации.
- Прогнать regression, мобильные тесты, проверку PWA scope на GitHub Pages и Netlify, тест установки Android/iOS. Не включать push-уведомления без отдельного согласия пользователей.

## Политика выпуска
Этап 1 допускается к тестовому деплою только после CI. Этап 2 не включать на основном сайте, пока сервер, миграция, очередь и RLS не прошли совместную проверку.


## Подготовленная экономная обработка (13 ноября 2026)
Реализована **только в исходном коде тестовой ветки**, НЕ в работающей Supabase:
- `supabase/functions/photo-batch-policy.js`: строгая проверка максимум пяти URL из приватного бакета, MIME+магические байты, размеры до 2400 пикселей/4 млн пикселей, максимум 5 МБ на фото и 15 МБ на пакет, SHA-256 и поиск одинаковых файлов.
- `supabase/functions/photo-batch-collage.ts`: серверная (не доверенная клиенту) сборка до пяти фотографий в один JPEG 3×2; повторная кодировка убирает EXIF/геоданные.
- `supabase/functions/fam-photo-batch/index.ts`: авторизованный приём и постановка файла в приватную очередь; публикации фотографий в этой точке нет.
- `supabase/functions/fam-photo-batch-worker/index.ts`: схема проверки кешированных хешей, одной новой картинки-коллажа через **только явно подтверждённый бесплатный** сервис и атомарной публикации проверенных фотографий. Никакого автоматического fallback на OpenAI.
- `docs/sql/photo-batch-cost-controls-DRAFT.sql`: приватная очередь, кеш решений одного владельца/версии политики на 30 дней, RLS и атомарный дневной лимит; значения по умолчанию запрещают любой вызов сторонней модели.
- `multi-photo-client.js`: ограниченная загрузка файлов и очистка незавершённых приватных загрузок.
- На странице переключатель `MULTI_PHOTO_UPLOAD_ENABLED = false` сохранён выключенным до завершения всех серверных проверок. Старый сценарий одного фото остаётся рабочим.

### До включения в производство
1. Создать настоящую миграцию через `supabase migration new` и применить её после тестирования на копии проекта, не на рабочей базе.
2. Поднять Edge Functions из исходников, подключить cron к worker; проверить RLS, подписанные ссылки, idempotency/cleanup, отказ модели, время выполнения и memory limits, включая реальные JPG/PNG/WebP.
3. Проверить и настроить конкретный **действительно бесплатный** vision endpoint, без платного fallback; подтвердить политику модели и качество распознавания мелких деталей в коллаже. Иначе очередь остаётся закрытой, без автоматического одобрения.
4. До отдельного подтверждения модели и бюджета не изменять `free_provider_verified=false`, `daily_request_cap=0` и `MULTI_PHOTO_UPLOAD_ENABLED=false`.
5. Защитить от изменения пользователями поля `listings.moderation_status` и владельца; проверить существующие политики UPDATE. Подготовленный endpoint пока не может доверять изменяемым пользователем признакам.
6. Проверить полный цикл на мобильном устройстве: выбор 2–5 фото → приватная загрузка → одобрение/отказ → галерея → удаление объявления и очистка всех изображений.
7. Перед выпуском отдельно устранить повторное поднятие потерянных в состоянии processing задач и очистку сиротских файлов.

**Почему блокировка обязательна:** веб-приложение для школьников не должно публиковать фото, которые не прошли действительную проверку. Код этапа не является подтверждённой функциональностью, пока SQL+worker+модель+тесты не работают вместе.
