# Штаб управления агентами FAM

Обновлено: 13 ноября 2026 года. Реализация штаба объединена в main; новые изменения подключаются только после тестов и одобрения PR.

## Назначение

Три независимые роли реализованы как ограниченный, бесплатный процесс GitHub Actions:
- **FAM ARBITER** сопоставляет файлы открытых PR, отмечает потенциальные конфликты; совпадение файлов не считается доказательством ошибки.
- **FAM INSPECTOR** проверяет техническое состояние локального Qwen-разработчика по GitHub Actions: повторяющиеся failures (3 за 7 дней), зависшие запуски (старше 2 часов), отсутствие запусков (48 часов) и нечерновые PR без обновлений (4 дня).
- **FAM RECRUITER** предлагает дополнительную специализацию только по подтверждённой повторяемой проблеме: 3+ пересечения PR, 3+ неудачных запуска кодера либо 4+ устаревших PR.
- **FAM INTEGRATOR** (координатор интеграции) группирует пересекающиеся PR в связанные кластеры, показывает черновики, защищённые файлы и рекомендуемую очередь проверки без автоматического выбора победившего PR. Эта роль использует те же ограниченные данные GitHub, что и ARBITER; отдельная LLM не запускается. RECRUITER больше не предлагает повторно нанять эту уже подключённую роль.

Это автоматизированные контрольные роли на фиксированных проверяемых правилах, **а не три отдельно запущенные языковые модели**. Новых платных API, весов LLM и подписок нет.

## Запуск и результат

- GitHub Actions: `.github/workflows/fam-agent-governance.yml`.
- Действие: `scripts/fam-agent-governance.mjs` с модулем `scripts/fam-integration-coordinator.mjs`.
- Тесты: `node --test tests/security/fam-agent-governance.test.mjs tests/security/fam-integration-coordinator.test.mjs`.
- После ручного merge workflow выполняется ежедневно в 04:45 UTC (07:45 МСК), либо по `workflow_dispatch`.
- Каждый прогон сохраняет вывод в GitHub Actions Step Summary.
- При обнаружении сигналов создаётся одна GitHub Issue с постоянным маркером либо обновляется уже существующая; отчёт не создаёт однотипные задачи каждый день.
- При отсутствии сигналов новый Issue не создаётся. Старые задачи автоматически не закрываются.

Проверка ограничена 25 текущими PR, 100 файлами на PR и 100 запусками кодера. Неполная выборка явно помечается в отчёте. Чтение и анализ происходят только по техническим метаданным GitHub: именам файлов PR, времени обновления, статусам CI, без содержимого личных сообщений FAM и без персональных данных школьников.

## Полномочия и контроль

GitHub Actions имеет только `contents: read`, `actions: read`, `pull-requests: read` и `issues: write` внутри job проверки. Действие может создать/обновить отчётную Issue. Оно **не может** изменять исходники, самостоятельно добавлять агентов, объединять PR, закрывать задачи, применять SQL, обращаться к Supabase и публиковать production.

Если RECRUITER предлагает роль, её технические полномочия, стоимость, отсутствие дублирования и тесты отдельно проверяются человеком. Для найма нужен отдельный PR и решение владельца FAM. Самовольное масштабирование команды запрещено.

Созданная роль не заменяет действующий контроль релизов, рецензента безопасности и человеческую ответственность. В FAM не оцениваются личные качества пользователей, школьников и реальных сотрудников по этой системе: оцениваются лишь технические признаки выполнения задач программными процессами.

## Что пока не реализовано

- Семантическое разрешение споров между PR по содержимому diff (текущая очередь проверки основана на пересечении файлов и статусе draft, а не на доказанном преимуществе реализации).
- Прямое чтение Supabase Worker или закрытых очередей — для этого потребуется отдельный защищённый read-only канал; запрещено обходить его.
- Автоматический найм (создание и включение новых кодирующих агентов) — намеренно только после разрешения владельца.
